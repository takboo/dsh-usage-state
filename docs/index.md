## 内容职责

| 文档 | 维护内容 | 更新时机 |
|---|---|---|
| 两份 README | 用户需要的安装、使用、来源、截图和关键限制 | 用户可见行为或要求改变 |
| 领域术语 | 领域词汇及概念关系 | 术语含义改变 |
| 用户排查 | 症状、检查顺序、现有限制与恢复办法 | 新增常见问题或修复缺陷 |
| 开发指南 | 工具链、本地回路、检查和贡献方法 | 脚本、工具或开发方式改变 |
| 设计共识 | 当前有效的目标、约定及已知实现偏差入口 | 设计决定改变 |
| 架构与验证 | 实际代码地图、数据流、测试能证明的范围 | 实现或验证方式改变 |
| 适配器指南 | 适配器契约、厂商字段语义和扩展步骤 | 新增/调整适配器或获得新接口证据 |
| 平台说明 | 有版本和来源的宿主行为 | 平台升级或新实验 |
| 发布与验收 | 可重复的发版、安装验证和市场维护流程 | 发布工具、规范或验证要求改变 |
| 待办清单 | 未完成事项的状态、优先级与验收标准 | 发现、推进或完成事项 |
| 更新日志 | 已发布版本事实与尚未发布的变更 | 发版前后 |
| 设计修订记录 | 决策变化的理由与代价 | 追加新修订，不重写历史 |
| 研究报告 | 标明日期、版本和来源的事实快照 | 新调查；勘误用显式补充 |

## 写作与维护约定

- 写清“设计要求”“当前实现”“已验证”和“待验证”，不以测试全绿代替功能完整或真机验收。
- 待办只在 Backlog 改状态。用户文档保留影响使用的简短说明并链接对应条目；审计的实施顺序属于历史建议。
- 当前流程不依赖某个人的 home 路径、缓存权限或某次安装日志；环境特例留在注明版本的记录中。
- 外部规则优先引用官方文档或固定 commit；调度时间、市场状态和在线 API 结论注明核验日期。
- 领域定义只放术语表；接口字段详解只放适配器/架构文档；README 不重复完整版本历史和开发回路。
- 研究报告中的本地路径、行号和“当前”都相对报告基线解释；后续变动以当前文档和 Backlog 为准。

## 链接与 npm 分发

仓库内部文档优先使用相对链接，便于离线阅读和分支审阅。README、更新日志和适配器指南会随 npm 包发布；它们链接到未随包发布的开发文档、代码或研究报告时使用 GitHub URL。

新文档应加入上面的任务导航，研究文件应加入研究索引。重命名文件时同步检查链接与锚点，不创建无读者、无维护职责的平行文档。
